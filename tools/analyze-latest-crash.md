# APEX Crash Report Analysis Guide

This document provides OpenCode with a structured workflow for analyzing
CDB crash reports generated by `tools\debug-apex.ps1`.

## When to Use This Guide

After a CDB session ends and a crash report file exists in `crash-reports\`,
OpenCode should follow these steps **before proposing any source code changes**.

---

## Step 1: Find the Newest Crash Report

```powershell
Get-ChildItem crash-reports -Filter 'APEX_CDB_CRASH_*.txt' |
    Sort-Object LastWriteTime -Descending |
    Select-Object -First 1 -ExpandProperty FullName
```

Read the full file. If it contains multiple crash sections (user ran the
debugger multiple times), focus on the **last** one.

---

## Step 2: Extract Exception Code and Faulting Address

Look for these patterns in the report:

- `ExceptionAddress:` - the instruction pointer where the crash occurred
- `ExceptionCode:` - the Windows exception code

Common exception codes:

| Code | Meaning |
|------|---------|
| `0xc0000005` | Access violation (null deref, use-after-free, etc.) |
| `0xe06d7363` | C++ exception (unhandled, re-thrown, or `throw` with no catch) |
| `0xc00000fd` | Stack overflow |
| `0xc000001d` | Illegal instruction |

The faulting address in an access violation tells you the type:

- `0x0000000000000000` through `0x000000000000FFFF` = **null pointer dereference**
- `0xFFFFFFFF80000000` and above = **user-mode bad pointer** (wild write)
- Any other unaligned address = likely **use-after-free or dangling pointer**

---

## Step 3: Identify the First APEX Frame

In the stack trace (after `kb` or `kv` output), find the **first frame**
that maps to an APEX source file. Ignore:

- Frames above it (OS kernel, ntdll, ucrtbase, etc.)
- Frames from `juce_*` modules (unless the crash is inside JUCE itself)

APEX source files live under:
- `My DAW\DAW_Core\Source\**\*.cpp`
- `My DAW\DAW_Core\Builds\VisualStudio2026\ArrangementEditor\*.cpp`

The frame format in `kb` output is:

```
# Call Site
DAW_Core!FunctionName+0x123 [path\to\file.cpp @ line]
```

The `@ line` tells you the exact source line.

---

## Step 4: Match Addresses Against the Correct PDB

Verify the symbol resolution is correct by checking the `lm` (list modules)
output. The line:

```
DAW_Core  00007ff6`12340000  00007ff6`15678000  DAW_Core.pdb
```

confirms CDB loaded the right PDB. If you see `* mismatched` or no PDB
listed, the symbol path may be wrong.

---

## Step 5: Inspect the Source Function

Using the file and line from the stack trace, read the **complete function**
surrounding the failing line. Read at least 50 lines above and below to
understand:

- What object is being accessed
- What the ownership model is (raw pointer, `juce::ReferenceCountedObject`,
  `std::unique_ptr`, `std::shared_ptr`)
- Whether there are thread-safety annotations or `juce::CriticalSection`
  guards

---

## Step 6: Trace All Relevant Callers

From the stack trace, identify every APEX frame above the faulting function.
For each frame:

1. Read the source function
2. Determine what parameters were passed down
3. Check whether the object was valid at the call site
4. Note whether the call originates from the audio thread, message thread,
   or a timer callback

---

## Step 7: Classify the Crash

Match the crash pattern to one of these categories:

### Null Pointer Dereference
- Exception `0xc0000005` at address `0x0`
- Look for unchecked `get()` on optional/smart pointer, or deleted component
  still referenced

### Use-After-Free
- Exception `0xc0000005` at a non-zero but clearly-invalid address
- Object was deleted but a callback or timer still references it
- Check `SafePointer`, `Component::SafePointer`, or raw pointer usage

### Out-of-Bounds Access
- Exception `0xc0000005` at an address near a known buffer
- Check `juce::Array`, `std::vector`, or raw array indexing
- Look for off-by-one in loop bounds

### Invalid Object Lifetime
- Crash during construction or destruction
- Virtual function call on partially-constructed or already-destroyed object
- `dynamic_cast` or `typeid` on destroyed object

### Stale Callback
- `std::function` or lambda capturing a raw `this` pointer
- `juce::Timer::startTimer` without matching `stopTimer` before destruction
- `juce::AsyncUpdater` triggered after object destruction

### Data Race
- No single clear faulting line; crash in a hot path
- Two threads accessing the same data without synchronization
- Check audio-thread vs message-thread access to shared state
- Look for `juce::AudioProcessorValueTreeState` accessed from both threads

### Plugin Unloading
- Crash inside a VST3 or AU plugin callback
- Plugin was unloaded but host still holds a pointer to it
- Check `PluginHostCore` lifecycle

### JUCE Component Ownership
- `juce::Component::getParentComponent()` returns null
- `juce::Component::getTopLevelComponent()` returns deleted object
- Child component outlives parent

### Audio-Thread / UI-Thread Violation
- `juce::MessageManager::callAsync` or `juce::AlertWindow` from audio thread
- GUI operation (repaint, setSize) from non-message thread
- Check for `jassert(messageThreadExists())` or thread assertions

---

## Step 8: Determine Root Cause vs. Symptom

**Critical question:** Is the stopped line the root cause, or is it where
previous memory corruption became visible?

Signs the stopped line is a **symptom**:

- The faulting address is far from any expected pointer value
- The stack trace goes through multiple unrelated subsystems
- The crash is in a very common function (e.g., `juce::String::operator=`,
  `memcpy`, `operator new`)
- The object appears valid but has garbage vtable

If the crash is a symptom, trace back through the callers to find where
memory was corrupted. Look for:

- Buffer overflows in adjacent objects
- Double-free of a shared resource
- Thread-unsafe modification of a container during iteration

---

## Step 9: Report File-and-Line Evidence

Before proposing any fix, present:

1. The exact file path and line number of the crash
2. The full function signature
3. The ownership chain from the stack trace
4. The thread that crashed
5. The exception code and faulting address
6. Your classification of the crash type
7. Whether this is a root cause or symptom

---

## Step 10: Propose the Smallest Safe Correction

The fix must:

- Address the **root cause**, not just the symptom
- Be the **minimal** change that prevents the crash
- Preserve all APEX real-time audio constraints:
  - No allocation, file I/O, or blocking in the audio callback
  - No GUI calls from the audio thread
  - Preserve PDC (plugin delay compensation) correctness
  - Preserve one-owner monitoring paths
- Not break existing functionality
- Be verifiable with the same CDB workflow

---

## Step 11: Build and Verify

After the user approves the fix:

1. Build x64 Debug: `& "C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\amd64\MSBuild.exe" "My DAW\DAW_Core\Builds\VisualStudio2026\DAW_Core.sln" /t:DAW_Core_App /p:Configuration=Debug /p:Platform=x64 /m /v:minimal`
2. Confirm build succeeds with exit code 0
3. **Never** claim the crash is fixed from compilation alone
4. Ask the user to re-run `tools\debug-apex.ps1` and attempt to reproduce
5. If the crash no longer occurs after reproduction steps, mark as fixed

---

## Reference: CDB Quick Commands

| Command | Purpose |
|---------|---------|
| `.exr -1` | Display the last exception record |
| `.ecxr` | Switch to the exception context |
| `kb` | Call stack with parameters |
| `kv` | Call stack with FPO info and parameters |
| `lm` | List loaded modules |
| `r` | Display registers |
| `dps @rsp L10` | Dump stack pointers (useful for finding return addresses) |
| `dt module!ClassName` | Display type layout |
| `!analyze -v` | Windows extension verbose crash analysis |
| `gn` | Go not handled (continue past first-chance exception) |
| `g` | Go (continue execution) |
| `q` | Quit debugger |
